Welcome. Today: a tour of "skills" for AI coding agents, and one skill collection in particular — Superpowers — that we've been using in our own work. ~18 minutes, questions at the end.

The bottleneck is moving

  • AI agents now write most of the code in agent-assisted projects — generating code is getting cheap
  • What's still expensive: deciding what to build and verifying it was built right
  • The question every team is wrestling with: how do we structure the work around the agent?
Frame the talk. Not "can AI code" — it can. The interesting problem is process: intent in, verified software out. Everything in this talk is one answer to that question.

A perspective we're forming

The industry is converging on a hypothesis: humans focus on specs and verification, agents handle the tedious middle.

It goes by "spec-driven development." We're still forming our own opinion — this talk is what we've seen so far, not a prescription. We'll come back to this at the end.

What is a skill?

A folder with a SKILL.md — instructions an agent loads when relevant.

my-skill/
├── SKILL.md          # required: metadata + instructions
├── scripts/          # optional: executable helpers
└── references/       # optional: docs loaded on demand

--- SKILL.md ---
---
name: systematic-debugging
description: Use when encountering any bug, test failure,
  or unexpected behavior, before proposing fixes
---
## The Process
1. Reproduce it. 2. Find the root cause. 3. ...
A skill is not a prompt you paste — it's a packaged procedure. Required frontmatter: name + description. The description is how the agent decides when to pull it in.

Progressive disclosure

1 · Discovery

At startup only name + description load — ~100 tokens per skill

2 · Activation

Task matches the description → agent reads the full SKILL.md

3 · Execution

Scripts and reference files load only if actually needed

Why it matters: you can keep a large library on hand without paying its full cost in context on every task.

This is the key architectural idea — and it will come back later when we talk about "skill bloat." Well-factored skills are cheap at rest.

An open standard, quickly

  • Oct 2025 — Anthropic announces Agent Skills for Claude
  • Dec 2025 — Spun out as a vendor-neutral open standard: agentskills.io
  • Within days — OpenAI adds Codex support; now 30+ agents: Claude Code, Codex, GitHub Copilot, VS Code, Cursor, Gemini CLI…
  • Distribution — plugin marketplaces (Claude Code), community catalogs, git repos

Skills you write are portable — not locked to one vendor's agent.

The point of this slide: skills are not a Claude gimmick. It's a small spec — a file format plus a loading model — and it got adopted across the ecosystem in months. Investment in writing skills carries across tools.

Enter Superpowers

  • A plugin of 14 skills covering the full SDLC — brainstorm → plan → implement → verify → review → merge
  • By Jesse Vincent (obra), launched Oct 2025; on Anthropic's official plugin marketplace; 280k+ GitHub stars
  • Philosophy: spec-first, test-driven, YAGNI, evidence over claims
  • The agent doesn't jump to code — it teases out a spec, gets your sign-off, then plans and implements
Superpowers = an opinionated methodology packaged as skills. It makes the agent behave like a disciplined engineer following a process — the author's framing. Now supports many harnesses beyond Claude Code (Codex, Cursor, Copilot CLI, etc.).

The skill map

using-superpowers→brainstorming→using-git-worktrees→writing-plans
↓ subagent-driven-development or executing-plans → finishing-a-development-branch
during implementation: test-driven-development systematic-debugging verification-before-completion
between tasks: requesting-code-review → receiving-code-review · plus: dispatching-parallel-agents writing-skills

Skills hand off to each other — you're expected to use them in sequence, not ad-hoc.

Anchor visual. Walk the main line left to right: entry point auto-triggers brainstorming before any creative work; worktree isolates; plans break work into 2–5 minute tasks; then execution either via subagents or in batches with human checkpoints. Cross-cutting skills fire on bugs, before "done" claims, and at review time.

Brainstorming: ceremony scales to the task

Spike

"Can we…?" A feasibility question. Probe cheaply, report a recommendation. No documents.

Bounded

Well-scoped change to an existing flow. Short design in chat, approval, go. No plan doc.

Architectural

New projects / subsystems. Questions → approaches → written spec → implementation plan.

Every path stops for your approval before implementation — the ceremony scales, the gate doesn't.

This classification arrived in v6.3.0 — earlier versions ran the full ritual for everything. The skill even lists "I'll call it bounded to skip the spec" as a red-flag rationalization. This talk's deck was itself built through this flow — meta-example if time allows.

The visual companion

  • Optional local web UI the agent opens alongside the terminal during brainstorming
  • Shows mockups, diagrams, side-by-side options — instead of describing UI in prose
  • Offered just-in-time, only when a question is genuinely visual
  • Caveat: can be token-intensive — worth it for UI-heavy work, skippable otherwise
Demo screenshot could go here if we capture one. The value: choosing between three wireframes beats reading three paragraphs describing them. The cost: rendering those artifacts burns tokens.

Plans → subagent-driven development

ARTIFACT — implementation plan (excerpt)

[ PLACEHOLDER — paste 2–3 tasks from a real plan: exact file paths, 2–5 minute granularity, verification steps ]

  • A fresh subagent per task; two-stage review (spec compliance, then code quality)
  • Main session stays clean — implementation noise lives in the subagents
The plan is written so a fresh agent with zero context can execute a task. That's the discipline: if a subagent can't do it from the plan alone, the plan was underspecified. Note: this mode needs prompting/capable models — more in risks.

Verification: evidence over claims

ARTIFACT — test report / verification output (excerpt)

[ PLACEHOLDER — paste real test-run output or a verification summary the agent produced before claiming "done" ]

  • test-driven-development — failing test first, always
  • verification-before-completion — no "it works" without command output to prove it
This is our favorite category of skill — it attacks the classic failure where the agent confidently declares success on broken code. Systematic-debugging similarly forces root-cause before fixes.

What we liked

  • Structure — spike / bounded / architectural means the right amount of process per problem
  • Approval gates — the agent stops and asks before building; fewer confident wrong turns
  • Visual companion — seeing options beats reading descriptions of them
  • Subagent leverage — a strong model plans; cheaper agents research, implement, verify in parallel
Ground each in a project anecdote. The overall effect: fewer restarts, better artifacts left behind (specs, plans, reports we could show colleagues — like today).

What to watch out for

  • Model choice matters — know which model and effort level fits each stage; small models are fine for research, poor for development
  • Token cost — thorough process = more input/output; the visual companion especially
  • Subagent ergonomics — sometimes in-context work beats dispatching; knowing when is a judgment call the framework won't make for you
Honest section. Our own rule of thumb: don't hand development tasks to the smallest models. And subagent-driven dev can feel clunky — handoffs fail in ways that in-context work doesn't.

The "skill bloat" question

The critique

  • Instructions + tools eat context before work starts; tool-selection accuracy drops as options grow
  • "Models plan competently unprompted — why pay tokens for harness?"

The counters

  • Progressive disclosure: a big library is cheap if well-factored
  • Consistency across a team is worth tokens
  • Alternative: grow small, project-specific skills from observed failures

Notably: critics rarely dispute the workflow — TDD, plan-first, review — they dispute paying for it on every task.

This is the most interesting debate. Minimalists (Ronacher, Hashimoto's "harness engineering") add one instruction only after a real observed failure. Anthropic's own guidance is closer to that than you'd expect: start from evaluated gaps, keep SKILL.md lean. Both sides agree on the practices — they differ on packaging.

Our take, by where you are

New / newish to AI-assisted dev

Try brainstorming with Superpowers — it teaches a good default process while you use it.

Experienced

Try a spec-driven skill set. Superpowers is a good one; GitHub Spec Kit, Amazon Kiro, and BMAD are also out there.

Advanced, with your own skill system

Skip adopting it wholesale — but it's worth a review for ideas to add to your toolbelt.

The recommendation is deliberately tiered — this is not "everyone must adopt Superpowers." Name the alternatives so people know the category is bigger than one plugin.

Where we think this is heading

We believe development is gravitating toward humans spending their time on technical specs and code artifacts — the intent and the verification — while pushing the tedious middle to AI.

Skill sets like Superpowers are early attempts at identifying and standardizing how. We're still forming our mental model — treat this as a perspective from our work, not a prescription.

Callback to slide 3. Sean Grove's "The New Code" framing is the intellectual anchor for the industry version of this idea; skeptics call it rebranded waterfall. We're watching, experimenting, and reporting — which is exactly what this talk is.
